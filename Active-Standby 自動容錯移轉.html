Active-Standby 自動容錯移轉與差異資料回補機制

雙機房高可用性（HA）叢集生命週期與資料一致性運作整理

1. 核心機制專業術語（Terminology）

① 仲裁管理者：叢集管理器（Cluster Manager / Orchestrator）

監控節點心跳（Heartbeat）、負責裁決誰是主機（Master/Active）與誰是備援（Replica/Standby）的中樞引擎（例如 AWS Aurora Storage Fleet、Patroni、Oracle Data Guard Broker）。

② 故障接管：容錯移轉（Failover / Promotion）

當主節點無預警失效時，備援節點由唯讀狀態（Read-Only）自動升格為可讀寫主機（Read-Write）接管營運的過程。

③ 角色對調：角色反轉（Role Reversal）

舊主機復原重啟後，系統強制將其降級為備援（Standby），並反轉資料複製方向（原為 A ➔ B，改為 B ➔ A）。

④ 差異回補：日誌追平（WAL / Binlog Catch-up & Resync）

新備援機透過交易日誌序號（LSN / Log Sequence Number），向現任主機索取離線期間產生的新帳務日誌並依序重放（Replay），達成「最終一致性」。

2. 機房主從狀態切換與自動閉環流程

階段一：平時正常營運（Active - Standby） A: Active ➔ B: Standby
[前台 POS / APP] ──(寫入交易)──> [機房 A (Active)] ──(同步日誌 WAL)──> [機房 B (Standby 唯讀)]

所有結帳發票與點數寫入 A 機房，A 透過低延遲專線將交易日誌複製給 B 機房待命。

階段二：A 機房故障，觸發自動 Failover A: 離線 ➔ B: 升級 Active
[機房 A (斷電/斷網)] ──(心跳中斷)──> [Cluster Manager 判定 A 死亡] │ ▼ (授權升級) [前台 POS / APP] ──(轉發寫入)──> [機房 B (自動升為 Active 承接業務)]

Cluster Manager 偵測到 A 連續心跳遺失，強制將 B 升級為 Active。前台連線指向 B，營運無中斷，新資料持續落入 B。

階段三：A 機房修復上線，自動角色反轉（Role Reversal） A: 降級回補中 ➔ B: 維持 Active
[機房 A 修復通電] ──(註冊重返)──> [Cluster Manager 強制 A 降為 Standby (防止腦裂)] │ ▼ (主動詢問差異日誌) [機房 B (現任主機)] ──(逆向回補斷線期間日誌)──> [機房 A (追趕進度中)]

A 重開機後不允許接收寫入，被強制設定為 Standby。A 自動向 B 查詢斷線期間累積的交易日誌，B 逆向將帳務回填給 A。

階段四：兩端完全同步，達成最終一致性 A: 健全 Standby ➔ B: 現任 Active
[前台 POS / APP] ──(寫入交易)──> [機房 B (Active)] ──(同步日誌)──> [機房 A (Standby 待命)]

A 將落後的資料完全追平（Lag = 0）。雙機架構自動完成自癒閉環，維持穩定營運，全程無需人工下指令倒資料。

3. 為什麼此流程「嚴禁人工介入」？

重大風險指標 人工介入處理之隱患 Cluster Manager 自動化控管
腦裂現象 (Split-Brain) A 恢復時若誤認自己仍是主機，兩邊同時接單，發票流水號與帳戶互踩覆蓋，造成不可逆損毀。 仲裁機制保證同一時間「全網僅能有一個節點具備寫入權限」，A 啟動時立刻鎖死為唯讀。
資料順序錯亂 工程師手動比對資料或倒 dump，容易遺漏外鍵關聯與微秒級交易先後順序。 依據日誌序號（LSN）逐筆精確重放，確保結帳、扣點、退貨時序 100% 吻合。
時間差延誤營運 人員半夜接獲通報、登入主機、撰寫 SQL 匯出匯入，平均耗時 1 至 4 小時。 系統秒級探測、自動建立逆向傳輸鏈路，復原時間（RTO）壓縮至數分鐘內。
災後切回建議（Failback 策略）：

當 A 與 B 重新打平後，業界普遍採「現任 B 繼續穩定當家」原則，避免二次切換風險；若需讓 A 恢復為主機，則排定於深夜打烊離峰時段發起數秒鐘的優雅主從調換（Graceful Switchover），對前線營業完全零衝擊。
