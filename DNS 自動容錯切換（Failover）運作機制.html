DNS 自動容錯切換（Failover）運作機制整理

商場雙機房架構容災原理與名詞對照解析

1. 核心機制正式術語（專業名稱）

① DNS 網址對應 IP：名稱解析（Name Resolution / DNS Query）

將人類看得懂的域名（如 api.crm.com）轉換為網路底層通訊用的實體 IP 位址（如 100.1.1.1）的過程。

② 發現故障並自動切換：DNS 容錯移轉（DNS Failover with Health Checks）

雲端 DNS 服務透過探針排程檢測後端伺服器健康狀態，當主機房連續心跳中斷，系統自動將解析記錄變更為備援機房 IP。

③ 口袋小抄的有效期限：TTL（Time to Live，存活時間）

DNS 伺服器告知用戶端（或 ISP）「這筆 IP 記錄可以暫存多久」的秒數設定值。TTL 過期後，用戶端必須重新向查號台查詢。

2. 生活化比喻 vs. 實際架構角色對照

生活化比喻角色 實際架構元件 在商場中的職掌
計程車司機 門市 POS 機 / 前台 APP 只認域名，不知道真實伺服器在台北還是高雄。
總部名稱 域名（Domain Name / FQDN） 例如 api.crm.com，長期固定不變。
104 查號台 權威 DNS 伺服器（如 AWS Route 53） 負責維護網址與 IP 的對應表，對外回報當前伺服器地址。
門牌地址 伺服器實體 IP（A Record） 真實機房的入口網路地址（主機房與備援機房各自獨立）。
巡邏員 健康探針（Health Check） 每隔固定秒數檢測機房是否正常回傳 HTTP 200。
口袋小抄 DNS 快取（DNS Cache / TTL） 端點為求速度自行暫存的地址記錄，時間內不再重新查詢。

3. 災難發生時的四階段自動演進

  1. 平時正常營運： POS 發起連線時查詢 DNS，取得台北主機房 IP（100.1.1.1），並將結果寫入快取（TTL 設為 30 秒）。封包直接送至台北。
  2. 台北機房斷線（自動探測）： 雲端探針每 5 秒送出一次請求。若連續 3 次無回應（約 15 秒內），系統正式判定台北機房離線。
  3. 告示牌自動變更（無人工介入）： Route 53 自動將 api.crm.com 對應的 A 記錄動態指向高雄備援機房 IP（200.2.2.2）。
  4. 快取過期與重新轉向： POS 機或各分店路由器內部的舊小抄（TTL 30 秒）陸續過期失效，發動新查詢後自動取得高雄 IP，連線無縫平移至備援機房。

4. 關鍵空窗期（1～3 分鐘）與地端架構防線

即便雲端可在 15 秒內更換記錄，但因外部電信業者（ISP）或作業系統常有「未遵守短 TTL」的快取延遲問題，實務上會有約 1 至 3 分鐘的解析切換空窗期。

商場防禦配套（Local Gateway + SQLite 離線緩存）：

在 DNS 解析尚未完全更新至備援機房的這 1～3 分鐘內，前線收銀不需在收銀台空等 Timeout。 門市端啟動 Local Gateway 進行離線開票與本機記帳，待終端取得高雄 IP 並恢復連線後，背景自動將單據回補，達成全館交易零中斷。
