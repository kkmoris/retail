百貨商場核心資訊系統架構選型評估與中台戰略分析報告

針對 1～9 大模組邊界劃分、選商生態現況、維運究責鏈條及中台建置精神研究

一、 百貨資訊系統九大模組定義與業務範圍
1. POS 與 EDC 管理
前台收銀、多元支付 EDC 整合、斷線續傳、發票取號開立、離線 SQLite 緩存。
2. 合約與專櫃維運
專櫃合約條款、抽成模式（純抽/包底取高/階梯抽...）、代扣費用、罰款、日月結 SOA(Statement of Account) 對帳、暫存傳票及發票換開等等。
3. 會員系統 (CRM)
會員基本資料、多卡號管理、晉級機制、標籤群組篩選、VIP 禮遇、點數活動、點數過期失效、金額補登調整及IFRS遞延費用計算。
4. 禮贈品系統
全館行銷活動設定（滿額/滿千送百..等等）、贈品進銷存、線上/現場贈品核銷兌換管理。
5. 財務系統
應收帳款 (AR)、應付帳款 (AP)、總帳會計 (GL)、出納與票據管理、預算控管。
6. 自營單品管理
自營單品基本資料、請採購作業、驗收、進退貨、批次變價、毛利計算與盤點、寄售作業。
7. 人力資源管理 (HRM)
複雜排班考勤（符合勞基法）、薪資獎金計算、教育訓練紀錄、績效考核、員工餐補...等等。
8. 請採驗與供應商管理
固定資產與消耗品管理、費用請採驗流程、資產盤點、維護使用記錄與非專櫃供應商合約建檔。
9. 券類管理
紙本及電子禮券/商品券/提貨券之發行、領用、退回、現場/人工核銷、防偽防重複核銷與銀行履約信託管理。
鐵律共識：「1. POS」與「2. 專櫃合約」在營運上為連體嬰。專櫃無合法合約，POS 絕對禁止營業；POS 的促銷折扣鍵、櫃位生效起訖日完全受合約條件控制，兩者絕對不可切割給不同廠商。

三、 台灣百貨軟體市場供應鏈真實生態

台灣百貨專櫃抽成（1,2 模組）因特有的「代收代付、包底抽、階梯讓利、預收發票換開」高度特化法規與商業習慣，形成了極端封閉的小型市場：

1. 宏誌科技 (RSL) 與 騰雲科技 (Turn Cloud) 的雙雄侷限

  • 宏誌 (RSL)： 產業元老，合約與抽成邏輯扎實，但架構偏傳統單體，面對現代雲端微服務與大型數位中台改版包袱沉重。
  • 騰雲科技 (6870)： 近五年承接大量日系（三井、LaLaport）與遠東新案，具備資本市場優勢；但市場也存在維護成本高、客製彈性硬等反饋。
  • 關鍵案例警訊： 新莊指標性大型商場「宏匯廣場」在開幕初期使用騰雲，後續因維運與營運考量，於實務上毅然抽換更換為致富寶 (ChiefPay)。此案例證明了騰雲在大型場域並非牢不可破，且致富寶已具備承接大體量全場營業之實戰能力。

2. 其他關鍵廠商之角色邊界定位

  • 致富寶 (ChiefPay)： 經宏匯實戰檢驗，在 1（POS/EDC）與 2（合約維運/SOA）已具備與傳統大廠抗衡之實力，為方案二中 1,2,6,9 的首選黑馬。
  • 鼎新數智 (Digiwin)： 全台 ERP 龍頭，但骨子裡為製造與流通供應鏈，絕不可讓其承接 12 專櫃抽成，應專注於 5（財務總帳）與 8（請採驗資產）。
  • 宣揚電腦 (JabezPOS)： 專長為連鎖品牌門市、專櫃品牌前台及餐飲 POS，並無大型百貨商場「全場數百櫃包底抽成合約主系統」之近期實績。
四、 多中台架構落地可行性與戰略推演
架構落地的先決條件：
中台架構絕非「外掛」，而是異質系統解耦與跨廠調度的核心樞紐。方案一（統包大單體）在現實中完全無法落實多中台架構；唯有採行方案二或方案三，自建之「業務中台層」與「全域 API Gateway」才具備存在的土壤與戰略價值。

1. 依據架構圖之四大防禦核心

  1. 地端 Local Gateway + SQLite 離線韌性： 各分店部署本地 Gateway 與 SQLite，發票字軌由雲端「發票中台」預先下發，結帳開票本地即時完成，再非同步拋轉雲端。外網斷線時前台營業零受阻。
  2. 全域 API Gateway + WAF 統一權責邊界： 外部所有 POS、APP、EC 連線均經 Gateway 驗證 Token 並產出 Trace-ID 稽核日誌。維運出問題時調閱 Log 儀表板，30 秒內精確鎖定出事之廠商模組。
  3. 傳票中台的解耦緩衝價值： 介於百貨營運模組與鼎新 ERP 之間，專責將抽成、自營、券類核銷轉化為會計暫存傳票，保護後端財務帳目純淨，不受前台頻繁促銷活動干擾。
  4. 數據中台隔離 OLTP 與 OLAP： 線上 Transaction DB 僅負責即時交易；報表、BI 工具、AI 應用中台（LLM/ML）全向數據中台取數，徹底免除分析查詢鎖死線上營運的風險。
五、 中台規劃的核心精神、主導權限與實施戰略
中台的核心治理哲學：
「規格自主掌權，實作交鑰匙外包。」
商場絕不能把中台規格制定權外放給任何單一廠商，也不必為了做中台而盲目招募龐大的內部開發團隊。CIO / IT 部門掌握中台大腦與規格制定權，工程實作則外包委託專業軟體商按圖施工，商場牢牢持有全套原始碼與主數據主權。
1. 主導權歸屬：為什麼必須由內部 CIO / IT 絕對主導？
  • 利益衝突迴避： 軟體商受限於自身產品利益，若由廠商主導規格，必會把中台定義成其自家產品的延伸黑盒子，扼殺未來抽換廠商的彈性。
  • 掌握數位主權： 中台是商場的神經中樞。誰制定了 API Contract、驗證機制、資料字典與稽核規則，誰才是商場未來十年的真正主導者。
  • 業務 Domain 的不可替代性： 百貨專櫃包底抽成、發票換開、贈品兌換、禮券信託等特化業務邏輯，僅有親歷現場的內部 IT 與營運團隊才能精準定義。
2. 外包實作戰略：如何落實「規格在內、編碼在外」？
  • 精簡內部編制： 內部 IT 團隊專注於架構治理、系統分析 (SA)、資安防禦與專案驗收；將大量的 API 編碼、微服務建置與前端串接外包給具備 AWS/雲端實力之專業 SI 團隊。
  • 原始碼所有權 (Code Ownership) 條款： 外包合約必須白紙黑字載明：中台系統之「全套原始碼、架構手冊、資料庫綱要 (Schema)、CI/CD 部署腳本」之智慧財產權完全歸屬商場所有，確保任何時期皆可隨時更換維護廠商。
  • 合約約束與標準規格綁定： 將《商場中台 API 接入與遵循手冊》直接作為採購合約附件，要求所有業務模組商（1269 廠商、34 MarTech、58 鼎新）必須無條件支援甲方中台規格。
3. CIO / IT 必須死守的五大中台工程防線
  1. 契約先行 (API First)： 廠商進場前必須先經內部架構師簽核 OpenAPI 3.0 / Swagger 規格書，明確輸入輸出參數與錯誤代碼 (Error Codes)。
  2. 全鏈路 Trace-ID 與統一日誌： 所有 Request 強制攜帶 `X-Trace-ID` 並貫穿全域 API Gateway 與各大中台，確保出問題時調閱 Log 儀表板，30 秒內查出故障來源。
  3. 高併發冪等性防護 (Idempotency)： 涉及扣款、發票、扣點與券類核銷之 API，必須實作冪等鍵，防止網路逾時重試造成重複交易。
  4. 前線非同步與熔斷降級 (Circuit Breaker)： 會員扣點與傳票生成強制走非同步佇列；當雲端中台延遲時，自動觸發降級策略，保證前台 POS 毫秒結帳不停擺。
  5. 高可用容器化與自動化容災： 中台服務全面容器化 (Docker/ECS)，納入 AWS 跨可用區 (AZ-B / Multi-AZ) 與 S3 跨區冷備份體系，落實 RPO ≈ 0、RTO < 1~3 分鐘之營運持續防禦。
