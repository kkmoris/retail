以商場第一線營運為本位 • 徹底破解「簡報吹上天、進場全沒有、事後猛加錢」採購死局 • 建立標準合約、驗收與範疇防禦體系

戰略核心宗旨在於：甲方必須具備主導制定標準的能力
企業採購大型 IT 系統的成敗，不在於開標時挑了哪一家知名廠商，而是在於甲方（商場）是否具備自行編撰高防禦性 RFP（需求建議書）的核心能力。缺少自編 RFP 能力的商場，只能被動接受廠商的產品型錄與標準合約，最終在「統包定義不明」、「必要功能拉扯」與「主觀驗收扯皮」的三重泥淖中被廠商牽著鼻子走。本白皮書從業務場景出發，將商業話術降維為法律死鎖與客觀數學指標。
一、 為什麼 RFP 必須以「業務場景（Business Scenarios）」為出發點？ RFP 靈魂核心

傳統 RFP 最致命的錯誤是寫成「技術名詞堆砌」或「靜態名詞清單」（例如：只寫『具備專櫃抽成功能』、『支援多元支付』）。廠商業務隨便看都能勾符合，進場後現場一跑卻大翻車。真正的硬核 RFP 必須以「動態業務劇本」為出發點：

  1. 靜態名詞可以打馬虎眼，動態場景無法遁形：當把需求定義為跨櫃促銷折抵、退貨發票換開、代扣水電與包底取高的連鎖動作時，廠商底層若無此邏輯便不敢輕易吹噓。
  2. 由業務場景倒逼架構約束，廠商無從抗拒：商場不需干預廠商底層程式語言，但透過「週六下午斷網 72 小時前台結帳開票不可停擺」的場景要求，廠商便必須無條件交出地端快取與離線高可用架構。
核心業務場景 傳統靜態清單（易鑽漏洞） 業務場景化寫法（老手實戰標準）
1. 專櫃拆帳與退換貨 系統需支援專櫃抽成計算與促銷折抵。 場景：顧客於 A 櫃使用全館滿千送百券消費，隔日跨館於 B 櫃辦理部分退貨。系統必須自動按比例回沖抵用券、重算兩櫃抽成，並正確換開發票與折讓單，對帳單 SOA 絕不可產生負數死帳。
2. 斷網容災與結帳 POS 系統需穩定快速，支援離線結帳。 場景：週年慶首日全館 200 台 POS 同步開票，在外部網路（光纖專線）實體拔除情境下，單筆結帳開票延遲仍必須小於 800ms，且連續 72 小時開票字軌絕不重號、跳號。
3. 會員跨通路點數併發 支援 APP 會員點數查詢與折抵扣點。 場景：線上電商搶購與線下專櫃結帳同時發生，會員於 1 秒內在 APP 與現場 POS 同時嘗試扣抵同一筆點數。系統必須具備分散式鎖與冪等性，強制一筆成功、一筆拒絕，絕不可超額扣點。
4. 財務日夜結自動過帳 系統需能提供日結報表並介接 ERP。 場景：每日夜間 23:00 各館營運結束後，營運數據自動拆解抽成、自營銷存、禮券核銷與手續費科目，於 01:00 前自動拋轉鼎新 ERP 生成暫存傳票，借貸試算平衡差額強制為 0。
5. 經營戰情高負載取數 提供歷史業績分析與報表匯出功能。 場景：營業下午 2 點人潮高峰，高層於戰情室拉取過去三年全館專櫃同期 YoY、MoM 巨量分析報表。運算必須走唯讀資料庫（Replica），前台 POS 收銀結帳速度不可受絲毫拖慢。
二、 統包系統架構約束與「交鑰匙（Turnkey）」真諦 邊界與範疇定錨

1. 何謂「交鑰匙總價包辦（Lump-Sum Turnkey）」？

宛如買房裝潢，統包商不能在施工中途宣稱「報價單只寫做木門，沒寫裝門把，門把一個加收 3,000 元」。「交鑰匙」意味著總價固定包辦，完工當天鑰匙交到商場手中，商場開門就能直接營運做生意。

  • 總價鎖死（Lump-Sum Fixed Price）： 除甲方主動提出全新業務模組追加外，乙方不得以任何藉口追加預算。
  • 功能必然附隨性（Inherent Functionality Rule）： 凡達成特定業務目的（如專櫃結帳）所必然伴隨之配套（退款、作廢發票、SOA 對帳單、暫存傳票），法律上直接推定包含於總價範圍內，不得視為額外客製。

2. 統包模式下 RFP 該如何寫「技術要求」？

在統包模式下，RFP 絕不能干預實作細節（Implementation）（如強求後端用什麼語言寫），但必須死守四大「架構邊界約束（Architectural Boundaries）」：

  • 可用性邊界： 明訂 POS 具備 Local Gateway + SQLite 離線 72 小時連續開票能力，杜絕純 Web 連線架構。
  • 通訊與對接邊界： 邊界強制提供標準 RESTful OpenAPI，且前端通訊必須接入甲方自建之全域 API Gateway，禁止私有黑盒直連。
  • 數據主權邊界： 數據 100% 歸屬甲方，乙方必須提供資料字典與即時唯讀庫（Read Replica），不得以保固為由限制存取。
  • 容災與 SLA 指標： 跨 AZ 自動容災（RPO≈0, RTO<3min），條碼掃描響應時間 P99<1 秒。
三、 破解「必要 vs 不必要」拉扯盲區：客觀判定尺規與人天池 終結文字遊戲

實務上，甲方常認為「不能退貨退稅我就開不了門，當然是必要功能」；乙方卻推託「別家都拿 Excel 算，系統沒做也能動，這算特殊客製」。化解此爭執需依循三大法規：

判定維度 法律與業務客觀標準 範例對照
1. 交易反向閉環原則 正向流程存在，其必然對應之反向沖銷、作廢、退款與折讓必須完整具備。 必要 既然能收券，就必須能退券、且產出信託核銷明細。
2. 法規稅務與防呆底線 缺少該功能將遭國稅局裁罰、違反法令或導致現場專櫃排隊暴動舞弊。 必要 發票折讓單自動上傳、合約到期自動鎖機。
3. 審計軌跡平衡原則 帳務對接時，借貸必須平衡，總帳餘額強制等於立沖明細。 必要 日結暫存傳票金額與前台銷售 100% 吻合。
4. 個性化偏好（非必要） 非核心流程，僅屬視覺美化、非標準動畫或個人化語音提示。 非必要 POS 介面節慶主題更換、3D 戰情立體圖。
老手防扯皮殺手鐧：總價內含「60 人天緩衝客製池（Scope Buffer Pool）」
在簽約總價中，強制要求乙方無條件提撥 50～80 人天之「彈性工時池」。當雙方針對某項目是否屬於「必要功能」僵持不下時，甲方有權啟動緩衝池直接扣抵工時，乙方必須無條件立即動工排程開發，絕不得以「待補簽報價單」為由延誤專案或停工要脅！
四、 展示口頭承諾「法證存證」與以甲方為準之「量化驗收標準」 終局驗收主權

1. 系統展示（Demo）口頭承諾之「法證級存證四步閉環」

業務在展示時口頭答應的細節往往未寫入簡報，事後工程師常以「當初沒這樣講」推諉。必須落實以下 SOP：

  • 現場全程錄影錄音存證： 評選展示與提問時全程錄音錄影，關鍵問答打上時間戳記（Timestamp）。
  • 會後 48 小時發出確認信： 會後甲方於 48 小時內條列《系統展示承諾與功能清單》正式寄給乙方主管。
  • 強制取得乙方主管信件正式回覆： 乙方必須於 3 個工作天內以 Email 逐筆回信確認「納入標準交付、不額外收費」。
  • 往來信件直接釘入合約： 該往來信件於簽約時直接作為合約附約，具備完全法定拘束力！

2. 驗收標準核定權限：乙方流程僅供參考，標準 100% 以甲方為準

  • 乙方流程僅供參考： 乙方可提供原廠既有之驗收腳本與清單，甲方大方參考以借用基礎案例，不重複發明輪子。
  • 合格判定權限在甲方： 最終上線驗收標準、量化效能指標與缺陷嚴重度判定，完全以甲方（商場）最終審定簽核之版本為準。
