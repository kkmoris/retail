環球資訊部：新舊系統交接（Cutover）與歷史資料轉移標準規範

核心轉移哲學：
「靜態底盤提前走、熱資料最後一夜收、海量歷史明細白天背景分階段搬；冷熱分離減包袱、複雜邏輯去狀態、極少特例走後台。」

一、 舊系統 5 大核心資料類別轉移策略

資料類別 轉移策略 實務做法與 ISO 執行標準
1. 合約相關資料 完整全量轉入 專櫃租賃條件、抽成級距與履約保證金採「提前靜態匯入」。切換前會同財會完成盲測對帳（UAT），舊合約轉唯讀加密封存至少保留 5 年。
2. 會員基本資料 全量轉入 + 增量 採「提前大宗底盤匯入 + 當晚增量同步（Delta Sync）」，當晚僅需同步打烊前最新註冊之會員，極速完成。
3. 會員權益（券類） 過濾轉入有效資產 砍掉過期雜訊，「只轉轉移當日仍有效的券」（`status = 'ACTIVE'` 且未過期），已使用與過期廢券留在舊系統，大幅減輕運算包袱。
4. 會員權益（點數） 快照結算 + 批次轉入 以當晚閉館打烊之「總點數快照 + 有效期批次（Lot-based Expiry）」轉入新系統當作期初餘額。歷史 VOID 沖銷走 API 回溯舊系統。
5. 會計總帳與交易明細 期初餘額 + 背景搬遷 總帳僅轉入「科目期初餘額（Opening Balance）」；歷史交易明細採「時間軸倒序分階段背景轉移」，冷資料不佔用深夜切換時間。

二、 海量交易明細：「時間軸倒序、分階段背景轉移」黃金戰略

針對需要耗費最多轉檔時間的歷史交易明細（例如 2 年內明細），採用「冷熱完全解耦、時間換空間」的敏捷轉移架構：

1. 階段性背景轉移計畫 (Phase-based Background Seeding)

  • 最後 3 個月熱資料（決戰 Cutover 當晚）：
    • 保留最近 3 個月的交易資料於切換當晚執行，確保開館時最常被調閱、退換貨的熱資料秒開。
    • 動態調整視窗（Agile Window）：最後留存的月數（如 3 個月或 2 個月），可依據前期背景試跑之實測效能數據（Benchmark）進行機動微調。
  • 1 年至 2 年前遠期冷資料（正式上線後白天執行）：
    • 上線後第一階段背景搬遷，於白天營運離峰時段寫入，不影響前線 POS 結帳。
  • 6 個月至 1 年前中期資料（第二階段背景執行）。
  • 3 個月至 6 個月前近中期資料（最後階段背景執行）。

2. 安全防護與自動化控制機制

  • 離峰限流防護（Throttling & Micro-batching）：背景搬遷程式設定 CPU/IO 門檻監控（例如 CPU > 50% 自動減速），以每批次 500~1,000 笔微分頁寫入，絕不鎖表。
  • 時間戳記智慧路由（Timestamp Threshold Routing）：後端設定全域時間開關（Time-window Flag），若查詢時間點小於「新系統已完成搬遷日」，APP / 客服 API 自動路由至舊系統唯讀備份庫抓取。

三、 點數 VOID 沖銷與 App 未同步更新之架構防線

1. 點數正負向與歷史 VOID 處理原則

  • 歷史交易 VOID 隔離：切換日前的歷史交易若於上線後發生退貨或 VOID 沖銷，新系統不處理歷史狀態機，而是透過 API 呼叫舊系統邏輯進行驗證與扣點。
  • 極少數特例實事求是（KISS 原則）：針對「搬遷中途被拿來辦理半年前退貨」等 0.01% 極端特例（Edge Cases），拒絕過度工程開發；直接「搭配樓管/客服人工後台進行扣點與單據調整」，並記錄 Audit Log 備查。

2. App 未同步更新之 API 轉譯防線 (Adapter Layer)

  • API Gateway 雙向轉譯（Adapter Layer）：在 App 與新後端之間架設 API 轉譯中介層，將舊版 App 請求自動翻譯成新後端規格，並保留至少 3 至 6 個月舊版 API 支援期。
  • 柔性引導與降級備案（Graceful Degradation）：若切換當晚發生預期外卡頓，App 啟動友善告示：「點數查詢升級中，不影響現場專櫃消費累點與折抵」，確保現場實體營運絕對不斷線。
ISO 簽核與開機紅線（Red Line）：
「切換當晚必須執行自動化校驗腳本（Reconciliation Bot），核對『會員總數、有效點數總餘額、有效券總張數』之 Checksum，經雙人複核完全吻合後，方可按下正式開機營運按鈕。」
